# Задание для Codex — диплом Netology IOSDT «Работа с сетью и хранение данных»

Ты работаешь **не над абстрактным примером**, а над полноценным дипломным UIKit-приложением для прогноза погоды. Выполняй работу **на Mac пользователя**, самостоятельно от начала до конца. Не ограничивайся планом, каркасом, красивым README или фразой «готово» после статической проверки. Не перекладывай действия на пользователя, если у тебя есть терминал и права их выполнить. Не задавай лишних вопросов: принимай разумные технические решения и фиксируй их в отчёте. Не обещай фоновой работы; доведи доступный этап до проверяемого результата в текущем запуске.

## Функциональные требования из Netology

1. Первый запуск: качественный onboarding с обоснованием доступа к геопозиции, вызовом системного разрешения через CoreLocation. При отказе приложение остаётся функциональным (пустое состояние с кнопкой «+» и ручным добавлением города). Не запрашивай разрешение бессмысленно на каждом запуске.
2. Основной экран погоды: название города, дата и местное время, текущая температура и погодное состояние, влажность, осадки, скорость ветра, восход/закат и **продолжительность светового дня**; адаптивная вёрстка на iPhone и iPad.
3. Добавление города через `UIAlertController` с текстовым полем; геокодинг введённого города в координаты, корректная обработка неоднозначных/не найденных городов и ошибок сети. Повторяющиеся города не добавлять. Не требовать платного API-ключа, если есть бесплатный подходящий источник.
4. Горизонтальный выбор нескольких городов с `UIPageViewController` либо равноценным навигационным компонентом и заметной индикацией текущего города. Для разрешённой геопозиции текущая локация может быть стартовым городом.
5. Прогноз на **7 ближайших дней** с прокручиваемым списком и кастомными ячейками; детальные показатели, иконки состояний. Настройки по макету.
6. Почасовой прогноз: горизонтальная `UICollectionView` на ближайшие 24 часа; экран «Подробнее на 24 часа», выбор часа/дня и корректное отображение времени в часовом поясе города.
7. Кэшировать **все показываемые погодные данные** локально через Core Data (допускается Realm, но Core Data предпочтительнее для этого проекта): при запуске **сразу выводить кэш**, затем обновлять из сети. Хранить города, координаты, прогноз, метку времени актуальности. Обеспечить офлайн-режим, отсутствие блокировок main thread, понятные loading/error/empty/stale состояния.
8. Настройка 7/25 дней из ТЗ: **не фабрикуй 25-дневный прогноз**. Open-Meteo предоставляет меньше 25 дней в обычном forecast API; если нет проверенного источника на 25 дней, честно оставь 7 дней, а 25-дневный режим объясни как недоступный/экспериментальный, не показывай фальшивые данные. Если найдёшь правомерный надёжный 25-дневный источник — реализуй переключение полностью.
9. Дизайн близко к предоставленным макетам, с сохранением читаемости, динамического текста, поддержки светлой/тёмной темы где применимо, Safe Areas, landscape/iPad, без захардкоженных экранных размеров.
10. Виджет — дополнительный пункт со звёздочкой. Делай только после полной и проверенной обязательной функциональности; если не сделан, явно обозначь это.

## Поставщик данных и архитектура

- Подходящий стартовый провайдер: **Open-Meteo** для current/hourly/daily forecast и geocoding. Перед интеграцией проверь действующие API-эндпоинты, поля, ограничения, attribution и timezone. Не утверждай наличие данных/дней, которые API не предоставляет.
- Раздели ответственности: `WeatherAPIClient`, `GeocodingService`, `LocationService`, модели `Decodable`, `WeatherRepository`, `CoreDataStack`/постоянное хранилище, view models (если уместны), UIKit controllers/coordinators.
- `URLSession` и тяжёлую работу с БД выполняй асинхронно; отменяй устаревшие запросы при смене города, не допускай гонок между городами.
- Конфиденциальность: никакие пароли, токены и приватные ключи в Git; .gitignore, необходимые permissions в Info.plist. Не менять существующие пароли пользователя и конфигурации сторонних проектов.
- Настройки и список городов должны сохраняться между запусками. Core Data schema/migrations должны быть валидными и открываться в актуальном Xcode; не повторяй ошибку `codeGenerationType="manual/none"` из предыдущей домашки.

## Реальные проверки — обязательно

1. Определи установленную версию Xcode и доступные SDK (`xcodebuild -version`, `xcodebuild -showsdks`) и доступные симуляторы. Не устанавливай большие Simulator runtimes без согласия пользователя.
2. Открой/исправь `.xcodeproj`: `xcodebuild -list`, затем **настоящий `xcodebuild build`** для доступного iOS Simulator SDK или generic destination. Обычный `swiftc -frontend -parse` **не заменяет** сборку. Исправь все ошибки компиляции, линковки, deployment target, Swift 6 concurrency, SPM и ресурсов.
3. Если есть runtime, запусти приложение и пройди вручную/автоматически UI-сценарии: разрешение/отказ геолокации, добавление и переключение городов, 7 дней, почасовой экран, кэш после перезапуска, поведение при отсутствии сети, поиск несуществующего города. Сохрани скриншоты и проверь визуально на iPhone/iPad.
4. Добавь и запусти осмысленные unit-тесты для JSON/DTO, геокодинга через stub URLProtocol, кэша Core Data и форматирования временных зон. Если test невозможно из-за отсутствия runtime, **не называй его пройденным**.
5. Сделай checklist соответствия каждому требованию Netology и отчёт с точными командами, фактическими PASS/FAIL, известными ограничениями и ссылками на скриншоты/артефакты. Не выдумывай результаты тестов.
